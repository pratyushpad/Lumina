## Retrieval pipeline defaults

`hybrid_rrf` (BM25 + dense fused with RRF, k=60) over the session's documents,
top-50 candidates, cross-encoder rerank to top-5. Query transforms
(`multi_query`, `hyde`) exist but are **off by default**: multi-query measurably
added latency without moving any retrieval metric (see the ablation).

## Headline finding

On the frozen set, **BM25 alone beats the shipped hybrid + rerank pipeline** on
every retrieval metric (recall@5 0.881 vs 0.869, MRR 0.811 vs 0.795, NDCG@10 0.818
vs 0.793) at 9 ms vs 287 ms p50. With 42 answerable questions the recall@5 gap is
one question, so the reading is "hybrid + rerank shows no measurable gain on this
set". The set favors lexical retrieval (limitation 2 below); whether dense and
rerank help on paraphrased queries is not yet measured.

## Evaluation method

- **Dataset**: `eval/dataset.jsonl`: 42 answerable + 10 unanswerable questions,
  frozen. Retrieval metrics are computed over the 42 answerable questions; the 10
  unanswerable ones test the refusal gate. Answerable items were drafted by an LLM assistant *from the actual chunk
  contents* and each `relevant_chunk_ids` entry was verified to contain the answer
  before freezing. Binary relevance.
- **Corpus**: 4 documents (2 arXiv papers incl. figure-heavy PDF, 2 authored
  markdown docs), ingested deterministically (`make ingest`; sha256 doc ids,
  stable chunk ids, manifest committed procedure).
- **Retrieval metrics**: recall@5/10, MRR, NDCG@10 computed directly in
  `eval/metrics.py` (numpy); ablation runs call the production `RetrievalPipeline`
  in-process.
- **Generation metrics**: faithfulness, answer relevancy, context precision,
  context recall: the RAGAS metric *definitions* implemented as direct judge
  rubric prompts in `eval/judge.py` (no ragas library dependency; prompts are
  inspectable). Judge calls throttled for API rate limits; when a subset is used
  to respect daily quota, the `n` is reported in `docs/eval.md`. The published run
  scored **n=18** answers (of 42 attempted) generated in July 2026 by Groq's
  `llama-3.3-70b-versatile`, a model since retired; it has not been re-run with the
  current default generator.
- **Refusal calibration**: threshold sweep of the top rerank score over answerable
  + unanswerable questions; false-refusal and false-answer rates reported per
  threshold. `MIN_RERANK_SCORE` is chosen from that table.

## Known biases and limitations

1. **Judge bias**: the published generation scores come from a Gemini judge
   (`gemini-flash-lite-latest`) grading Llama answers. Cross-family judging avoids
   same-family self-preference but not judge bias in general. A re-run with the
   current default generator (`gemini-2.5-flash`) and a Gemini judge would be
   same-family, which tends to inflate scores; prefer a judge from another family. Treat absolute generation scores with
   skepticism; retrieval metrics and ablation *deltas* are the reliable signal.
2. **Lexical bias in the eval set**: questions largely reuse source-chunk
   vocabulary, favoring BM25 over dense retrieval. Dense retrieval may close the
   gap on paraphrased queries; the eval set does not currently measure that.
3. **Small corpus and set**: 4 documents / 363 chunks, 42 answerable questions,
   no confidence intervals. The refusal sweep is flat (0% / 0% at every
   threshold) because the 10 unanswerable questions are clearly off-topic, so it
   does not discriminate between thresholds. Latency numbers (p50 per stage) are
   not representative of large corpora; the BM25 index is in-memory and
   single-worker by design at this scale.
4. **Binary relevance**: NDCG uses binary gains; graded relevance judgments were
   not collected.
5. **tokens/sec**: local-model throughput is measured per request from streamed
   usage. Values marked with `~` in the UI are estimated from character counts
   when the backend returns no usage data.
